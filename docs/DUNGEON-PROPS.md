# Dungeon props

The original prop library that replaced the dungeons' cartoonish CC0 props
on 2026-10-11, and how to add to it. Philip's order: "replace cc0 props in the
dungeons that look cartoonish with your own creations." The dungeons
themselves are in [DUNGEONS.md](DUNGEONS.md).

## What it is

Dungeon modules still call `kit.props.place({ file: 'props/Barrel.gltf', ... })`
with a CC0 path, exactly as before the swap. `PropPools`
(`client/src/dungeon-kit/instances.ts`) looks the path up in the swap index
(`client/src/dungeon-kit/dprops-index.json`). When the index names an original
prop for that file, the placement goes to that prop's pool instead, re-fitted
to the size the CC0 model had where it stood (`props-swap.ts`). The originals
are generated by `tools/assets/build_dungeon_props.mjs` from family files
`tools/assets/dprops/fam_<pack>.mjs`, one GLB of named meshes per family, and
all of them draw with ONE material on ONE shared original atlas.

So **flipping a CC0 file to an original is a line in a family file and a
rebuild, never an edit to a dungeon module.** No module was edited for the
swap.

Why this shape: the CC0 kits read as toys beside the authored architecture
(fat octagonal bevels, flat colours, blob forms). The props are small
parametric objects (boards, staves, lathes, tubes) that need no booleans or
modifiers, so a node generator in the mould of `build_heartwood_lamps.mjs`
(raw vertex data, one GLB, read back without the glTF loader) builds them
deterministically in a few hundred ms with no Blender install, and the node
tests import the same library.

Where it stands: **115 of the 159 CC0 files the dungeons placed (1,484 of
2,388 placements) are replaced**: 111 by 83 original props in 11 packs, and 4
tree files by the open world's generated trees. **44 files (904 placements)
are kept** as CC0, listed below with the reason. Draws per view went down,
not up: 2,498 to about 2,418 over the 44 dungeon views (the fix pass's
book-row removal took 2 more off its 20 views), every view equal or lower
except the Beacon Fort's mid view, 52 to 53 (a crate stack's far mesh drawn
beside its near one). The reason is one draw per prop id: four barrel files
are one `cask` pool, four chest and trunk files one `chest` pool, six bottle
files four pools.

## How a module asks for a prop

`kit.props.place({ file, group, x, y, z, yaw, scale, far })`, as for any CC0
prop: `file` is a key of `client/src/env_manifest_cc0.json`. In
`PropPools.load()` each placement resolves one of three ways:

1. **The swap.** `resolveSwap(DPROP_INDEX, placement, theme)`: the index names
   the file, so the placement joins the original prop's pool with a new
   position, yaw, scale and instance colour.
2. **A nature route.** `natureTemplate(scene, file)` returns a generated tree
   for the four routed tree files; it pools by file like a CC0 prop.
3. **The CC0 file itself** (one of the 44 kept files, or anything not in the
   index), loaded and pooled as before.

`file: 'dp:<id>'` places an original by its id, with no CC0 file behind it.
`raw: true` on a placement draws the CC0 file as itself even when the index
replaces it (the prop sheet's "old" column).

One draw per prop id in view, whatever the count. A prop with a far mesh is
two pools: near rooms draw the near mesh, `far: true` placements in far (LOD)
rooms draw the far one, so it costs a second draw only when both are on
screen. A small prop (largest side up to 0.45 m) is never drawn in a far room,
whatever the placement says.

## Authoring a prop

```js
import { TAU, RX, RY, RZ, T, SC, chain, smooth } from './lib.mjs';
export const PACK = 'vessels';                       // the GLB is /models/dprops/vessels.glb
export const PROPS = {
  urn_lidded: {
    far: true,                                       // also build a far mesh; omit for small props
    build: (m) => { ... },                           // runs twice: m.near true, then false for the far mesh
    tint: { tomb: '#c8c0b0' },                       // per-theme instance colour ('*' = every theme)
    replaces: { 'graveyard/urn-round.glb': {}, 'props/Vase_4.gltf': { fit: 'height', scale: 1, tint: { '*': '#a09080' } } },
  },
};
```

Prop ids are global across packs; name them for what they are
(`bookcase_narrow`, `rubble_spill`), not for the CC0 file. A new family is a
new `fam_<pack>.mjs`: the generator and the test pick it up from the folder.

**Space.** Babylon's: y up, metres, left-handed. A prop stands on y 0 (the
generator fails one that does not), its plan centred on the origin, its
**front toward -z**. Author at real sizes (a chair seat 0.45 m, a table top
0.75-0.8 m, a barrel 0.9 m) and near the CC0 file's typical placed size, so
the fit lands near 1.

**The library** (`lib.mjs`; its header and each method's comment are the
reference):

- `m.box(min, max, { region, endRegion, grain, bevel, skip, ... })`: a
  bevelled box whose chamfer and corner normals are the neighbouring faces',
  so an edge catches light like a rounded arris. `skip: ['-y']` drops faces
  nobody sees.
- `m.lathe(profile, sides, { inside, around, a0, a1 })`: a surface of
  revolution; the profile runs **bottom to top**.
- `m.grid(rows, cols, pos, nrm, st)`: any parametric surface (staves, cloth,
  a curved lid); `m.tube`, `m.disc`, `m.poly`.
- `m.at(chain(T(...), RY(a)), () => ...)` builds under a transform (`chain`
  applies the last one first; mirroring is handled).
- `m.rand()`, `m.vary(0.1)`: seeded per prop id, so the same source writes the
  same bytes. Plank-to-plank tone is most of what makes wood read as wood.
- `m.near`: skip detail when false to build the far mesh from the same
  function (`fam_casks.mjs cask()` is the pattern).

Families export their helpers for each other; import, never copy. The ones
worth knowing: `cask`, `rivet` (casks); `surf`, `blob`, `drape`, `panel`,
`turned`, `bail`, `hinge`, `ringPull` and tableware (furniture); `longsword`,
`heater` (metalwork); `book`, `bottle`, `crock`, `moulding` and the absolute-UV
helpers `cellUV`, `polyUV`, `gridUV`, `latheUV`, `bandUV` (books); `sheet`,
`blade`, `leaf`, `stem`, `settleWinding`, `finish`, `floorClamp` (plants).

Casework is real frame-and-panel (`panel()` in `fam_furniture.mjs`, used by
the cupboard, the dresser, the bed ends and the carcass sides). Stiles run the
full height with rails between them, and the grain runs along each member.
The fielded panel sits 16 mm back in the frame, with four bevelled margins
that catch the light. Drawers carry a lighter, proud cockbead. Backs are
vertical boards with hairline joints (`boardedBack`). The first cupboard
showed its back as a flat slab of diagonal grain, and the swapped sheet tile
shot Quaternius casework from behind. So shoot casework from both sides.

**Colour.** COLOR_0 multiplies the atlas: `tone x dye x shade x contact`.
`dye` colours the near-white regions (`wool`, `velvet`, `glazed`). The contact
shade is the prop's own ambient occlusion: every vertex darkens toward the
floor, from `m.contactLow` (0.55) at y 0 to full at `m.contactH` (0.22 m). It
is stored as bytes, so a tone above 1 clamps; brighten in the atlas, not the
tone.

### The atlas

One 2048 sheet at 256 px per metre, one material for every prop:

- six **wood strips** 4 m x 0.5 m, grain along U: `oak`, `oak_dark`, `pine`,
  `weathered`, `beech`, `walnut`;
- 1 m **cells**: `endgrain`, `bark`, `iron`, `iron_rust`, `brass`, `gold`,
  `steel`, `pewter`, `linen`, `burlap`, `wool`, `velvet`, `leather`, `rope`,
  `parchment`, `paper_edge`, `terracotta`, `glazed`, `glass`, `wax`, `stone`,
  `marble`, `bone`, `straw`, `coal`, `produce` (quarters), `spines`, `label`,
  `emit` (the only emissive cell: flame, coals, lantern glass), `soot`,
  `plaster`, `leaf`;
- 128 px **swatches** (every UV at the centre): `white`, `black`, `grey`,
  `gilt_flat`, `red`, `blue`, `green`, `iron_flat`, `flame`, `ember`,
  `shadow`, `cream`;
- nine **package cells**, painted by `pkg_<a|b|c>_paint.py`.

Specular and gloss are per region: wood dull, iron satin, brass and gold
bright, glass and glaze sharp. The package cells default to matte (spec 0.06).
The coin hoard `pkgB2` is spec 0.75 / gloss 0.65, so the mound glints like
the loose coins on `gold`. A face's UVs are fitted INSIDE its region at a
seeded offset, never wrapped: no seams and no two planks alike. A face bigger
than its region (over 4 m of wood, over 1 m in a cell) is squeezed, so split
long surfaces into boards, which is what they are anyway. A design that must
show whole (a book spine, a glaze band, a banner face, a leaf) cannot use the
fitted UVs, which land at a random offset: address it with the absolute-UV
helpers in `fam_books.mjs`.

`atlas.py` is deterministic: two people repainting in turn converge on the
same sheet. `--preview [out.jpg]` writes a labelled map to the path given, or
by default to `tmp/dungeons/polish/props/atlas_preview.jpg`.

Wood grain runs nearly straight. In the first atlas the strips' drift and fan
were steep, up to about 55°, so any 0.3-0.5 m window showed diagonal grain:
a door field, a drawer front, a panel. `paint_wood` now drifts 0.13 of the
strip's height (it was 0.32) and fans 0.16 (it was 0.45). That change reached
every wood prop. The bark cell was repainted lighter and warmer: plates broken
across the fissures, lichen on the ridges, mean albedo 0.32 (it was 0.20).
Burlap is now a fine open weave about 1 cm across, with slubs along warp and
weft, so it reads as coarse cloth at a dummy's or a root ball's size.

### Budgets and the LOD rule

| class (largest side) | triangles, near | far mesh |
| --- | --- | --- |
| small (up to 0.45 m) | 700 | none: small props are never drawn in far rooms |
| medium (to 1.3 m) | 2,400 | optional, at most 30% of near |
| large (over 1.3 m) | 6,000 | recommended, at most 30% of near |

The generator fails a prop over its budget or a far mesh over 30%.
`budget: n` (or `size: 'large'`) on a prop overrides the class. The generator
writes the override into the prop's index entry (`budget`, only when it
differs from the class), and the test checks `p.budget ?? BUDGET[class]`, so
both enforce the same limit. Say why in a comment. No prop uses an override
yet.
Give a far mesh only to props a module places `far: true` (stacks, carts, big
furniture, rubble, the palm): fourteen props have one, and a far mesh no
placement uses is never drawn.

## Swap entries

`replaces: { '<CC0 path>': entry }` on a prop, then rebuild. The prop's plan
centre lands where the CC0 model's plan centre stood (the generator copies the
CC0 bounds from `env_manifest_cc0.json` into the entry's `from`). A CC0 path
may be claimed by one prop only; the build fails otherwise, and on a path the
manifest does not know. Entry fields, all optional:

- `fit`: `'height'` (default) scales the prop uniformly so its height equals
  the placed CC0 height, so every usage keeps its own scale while the
  proportions stay real. `'footprint'` matches the larger plan side (rugs,
  plates, loose paper, coin piles, stacks whose CC0 height was mostly air).
  `'real'` ignores the placement's scale (bones, the skull, the coffin, beds,
  the pan: the CC0 ones were 1.6-2.5x life). `'placement'` is the authored
  size times the placement's scale, for a prop authored at the CC0 file's own
  size (the banners).
- `pivot: [x, y, z]`: a point in the CC0 file's frame, scaled and turned with
  the placement, where the new prop's ORIGIN lands, in place of matching plan
  centres and bases. Use it when a prop must hold a point the module built at
  every scale: the banners' sleeve on the Mausoleum's rod
  (`HANG = { fit: 'placement', pivot: [0, 0.53, 0], dyaw: π }`), the keyring's
  board on the wall (`pivot: [0, -1.196, -0.045]`).
- `scale`: a factor on top of the fit (the bench's 0.868 makes it a real
  2.4 m bench, not the CC0's 2.78 m).
- `offset: [x, y, z]`: in the prop's own frame, after the fit, unscaled.
- `dyaw`: added to the placement's yaw, for a CC0 model that does not face
  -z (19 entries carry a half turn).
- `tint: { '*': '#a08e80', furnace: '#...' }`: this file's instance colour.
- `to: ['a', 'b']`: variants picked per placement by position. Each variant
  is a pool and a draw: use it only where a room needs two looks; prefer one
  prop tinted per file.

## Tints

One instance colour multiplies the whole prop, atlas and vertex colour alike:
the entry's tint for the file times the prop's own tint for the theme (keys
are the `THEMES` keys: tomb, lodge, ballroom, belltower, cellars, furnace,
sluice, granary, watchtower, beaconfort, keep; `'*'` for all; the Great
Watchtower's is `watchtower`, not its zone key). No tint means no colour
buffer at all. The ones in use: Barrel_Dark `#a08e80`; the Lodge's dark oak
(`#bca896` to `#d0c0b0`, its cupboards `#e2d6ca`); the Furnace's soot
(`#a49488` to `#b8aa9c`); the Beacon Fort's `#b0a69c` to `#bdb2a6`; the
tomb's rubble `#e2dcd2`; the training dummy `#d8d0c4` everywhere.

Dungeon light is low and a tint darkens iron and wood together: keep tints at
0.6-0.8 of white and look. Where a tinted wood went murky, a lighter wood
strip untinted served better (the Lodge's bunks are pine, untinted).

## Nature files

`props-nature.ts` routes four CC0 tree files to the open world's generated
trees, the nature remake Philip approved: `nature/CommonTree_1`,
`nature/CommonTree_5` directly, `CommonTree_3.glb` as the broadleaf and
`CommonTree_Dead_1.glb` as the bare tree, each fitted to the kit file's
measured bounds. Each template is built fresh (its own geometry, so the pool's
thin-instance buffers are its own), its far double disposed (the room culler
replaces it), never a shadow caster. They keep the world's wind sway, indoors.
The kit files themselves are deleted (the loose ones with the dungeon pass, the
`nature/` folder on 2026-10-18); the paths remain as keys, and the manifest
keeps their rows.

The world's small plants were tried first for the Glasshouse's ferns, pot
plants and flowers and read as spiky cones at a seedling's 20 cm, so those
four files, the palms, the ivy and the log are atlas props in
`fam_plants.mjs` instead: leaves are two-sided geometry on the `pkgC3` leaf
cell, no alpha, so they share the one opaque material.

## Build, check, look

```sh
# from the repository root
python3 tools/assets/dprops/atlas.py [--preview out.jpg]   # only after a paint change
node tools/assets/build_dungeon_props.mjs [<pack> ...]     # one family or all; merges the index
node --test client/test/dungeon_props.test.mjs
npx --prefix client tsc --noEmit -p client
```

A dev server picks up a new GLB and index on a reload.

**The prop sheet.** `/prop-sheet.html` draws each item alone in a dungeon
corner (the kit's floor and wall sheets, a theme's hemisphere, fog, tone
mapping and one lamp) beside a 1 m post, through `PropPools`, so it shows
exactly what a dungeon draws. `props/Barrel.gltf` is the CC0 file raw (a
file still on disk),
`props/Barrel.gltf>` the same file through the swap, `dp:cask` an original by
id. Arrow keys step through the items; `&shoot` leaves a PNG in
`window.__propSheet`.

```
/prop-sheet.html?items=dp:cask,props/Barrel.gltf,props/Barrel.gltf>&theme=lodge&cols=6
```

**In the room.** Look at the prop where a module put it, not only on the
sheet: the sheet hides fit and placement mistakes that only show in place (a
cloth inside a wall rail, a sack in the wrong part of a wagon).

**The replaced CC0 files are deleted** (2026-10-11, at the merge): 140 model
files the old dungeons or the swap keys named and nothing fetches any more.
The modules still place their paths as swap keys, so the raw sheet item and
the old `?cc0props` before/after switch are gone for them; the before
sheets were local scratch and are not kept. Their measured bounds stay in
`env_manifest_cc0.json`, which `build_dungeon_props.mjs` and
`dungeon_props.test.mjs` read: `gen_cc0_manifest.py` carries an entry whose
file is gone over from the old manifest while `dprops-index.json` swaps it (or
`props-nature.ts` fits a tree to it). Thirty swap keys keep their file on
disk because the open world still places it (`props/Barrel.gltf`,
`props/Wagon.gltf`, `graveyard/urn-round.glb`, ...); the dungeons draw the
original in its place. A NEW swap must name a file still on disk
when it is built. On 2026-10-18 every CC0 file nothing fetched or named went
too, the dungeon kit's unused KayKit pieces among them (CC0-ASSETS.md "The
CC0 packs"); the Quaternius files under "What is kept, and why" were all still placed and
stay.

**Counts.** `tools/qa/zone_counts.mjs` with
`VANAI_VIEWS=tmp/dungeons/views.json` (a local viewpoints file, not in the
repository; DUNGEONS.md) is the budget check. A
swap should be draw-neutral or better.

The scripts that shot the sheets and rooms for the 2026-10-11 work
(`sheet.mjs`, `compare.py`, `rooms.mjs`, `counts.mjs`, `capture.mjs`, which
wrote `placements.json`, every placement in the eleven dungeons) were
scratch and are not in the repository, nor is the inventory that held the
verdict and reason for each of the 159 files. Write a tool under `tools/qa/`
before relying on any of that.

## Tests

`client/test/dungeon_props.test.mjs` (in `npm test`):

- the swap maths: the height fit keeps the placed CC0 height; the new plan
  centre lands on the CC0 plan centre under yaw; footprint and real fits;
  small props never far; tints multiply; a `pivot` lands the prop's origin on
  its CC0-frame point, scaled and turned with the placement;
- the library: a bevelled box faces out under a mirroring transform too, with
  UVs inside its region; lathes and tubes face out; atlas regions sit inside
  the sheet and never overlap;
- the packs: every prop inside its budget, standing on y 0, present in its
  GLB with the indexed triangles and bounds, and **no face turned in once
  read back the way `loadPack` reads it** (x negated back, the winding left as is);
- the index: every swap names a known CC0 file and an existing prop, and the
  index is current with the family files (rebuild the pack when it fails).

## Traps

1. **Contact shade darkens flat props.** Everything within 0.22 m of the
   floor is shaded toward 0.55, so a plate, a page or a platter came out 55%
   dark all over and read near black. A flat prop lifts its contact shade
   (`fam_books.mjs flat()`: `contactLow 0.8`, `contactH 0.012`).
2. **Inward faces.** A face is front when `cross(b - a, c - a) . n < 0`;
   every primitive orders its triangles from the normal you give, so a wrong
   normal turns a face in, and a culled face shows the room through the prop.
   A grid quad bent across its diagonal (a leaf's twist, a sherd's edge, a
   plate rim's hairpin) can leave one half wound against its normals:
   `settleWinding` (`fam_plants.mjs`, applied by `finish()`) rewinds every
   triangle to its normals and drops zero-area ones. The test catches what is
   left.
3. **Lathe profiles run bottom to top.** Reversed, the normals point in; for
   an inner wall pass `inside: true` with the profile still bottom to top.
4. **Gaps need a back.** Boards with gaps over nothing show the floor through
   the prop. Put a dark core behind them (`region: 'soot', bevel: 0`, the
   crate's inner box, the plate stack's core) or make the joint a V-groove
   (the cask's staves).
5. **A dark cell reads black in dungeon light.** The first `bark` cell had a
   mean albedo of about 0.2, and a log on it read black in every dungeon. The
   log moved to `weathered` in four quarters, with the seams reading as
   checks. Later the cell itself was repainted to 0.32. Measure a new cell's
   mean before you use it on a big surface.
6. **A coarse cell squeezed onto a big surface reads as something else.** The
   first `burlap` weave, about 2.7 cm, squeezed onto a 1.6 m sack in one
   patch, read as basketwork. The sacks became `linen` dyed to jute, in two
   sewn panels at true scale. Burlap was repainted to a 1 cm weave and is kept
   for small users.
7. **Plan centre is not the pivot.** By default the swap keeps the CC0 model's
   plan centre and scales by the placement. An `offset` is unscaled, so it
   cannot hold a point (a rod, a hook) at every scale. Use the entry's
   `pivot`. The Mausoleum's `hangBanner` builds a brass rod at the placement
   origin, and the CC0 cloth hung 0.4-0.7 m in front of it. The banners first
   held their sleeve on the rod with an ANCHOR vertex, a stray vertex with no
   triangle that bent the bounds. `pivot` with `fit: 'placement'` replaced it.
   Over all 30 placements the rod moved at most 1.3 mm, and the cloth's
   0.16 % anchor artefact went. KayKit wall pieces hang on their origin line,
   not their back plane. The rebuilt keyring's `pivot` puts its board's back
   where the first version's was.
8. **CC0 files do not agree on facing.** Our props face -z; the Quaternius
   casework, bookcases, lectern and Chair_3, KayKit's wall shelves, keyring,
   trophy and banners, and the shrine face +z and carry `dyaw: Math.PI`. Check each file from
   both sides on the sheet.
9. **The height fit follows the CC0 height.** A prop much shorter than the
   CC0 model was is scaled up in every dimension (the keg on its stand went
   to 1.27 m). Use `fit: 'footprint'` or `scale` where the CC0 height was
   mostly air.
10. **CC0 origins sink or float.** Bones were centred on their origin (half
    under the floor), dirt tiles sat 0.1 m down, the vines hung below their
    origin, the sword shelf sank 13 cm. Fix it with the entry's `offset`, not
    the module.
11. **Tints multiply everything** and the light is low: the first dark-oak
    tint on the Lodge's casks went nearly black. Keep tints light (above).
12. **Lighting is not the props' job.** Props draw with their own material
    (`dprops_atlas`); a theme's emissive floors on the kit's materials do not
    reach them. If a room's props read dark, that is the room's lighting
    (DUNGEONS.md "Lighting"); do not add emissive to props.
13. **Thin-instance buffers live on the geometry**: every pool gets its own
    VertexData (`dpropMesh`), never a shared one.
14. **Do not hand-edit the index.** JSON writes `-0` as `0`; the generator
    rounds through `|| 0` so the test compares equal.

## Outside the dungeons: the Kings' Gardens' statuary

The library builds props for the open world too. Philip ordered, on 2026-10-11:
"find out what the missing models in kings garden are and replace it with your own".
`tools/assets/build_garden_statuary.mjs` builds the parterres' three garden pieces with
`lib.mjs` on this atlas. Each one stands on its own moulded pedestal:

- `garden_urn`: a campana urn with a gadrooned bowl and stone scroll handles fixed at both ends, open and filled with soil.
- `garden_obelisk`: an obelisk on steps with a gilt pyramidion.
- `garden_armillary`: an armillary sphere on a baluster.

They replace CC0 graveyard pieces that stood on box plinths. One of those plinths never loaded
a model: `statue()`'s `kind` came in negative and asked for `/models/undefined`.

Each piece is its own GLB in `public/models/dprops/garden_<piece>.glb`. `placeExact` loads it
with the stock glTF loader, so `glb()` gets a `look`: the atlas's diffuse and normal maps as
glTF textures. The files sit beside the atlas because Babylon's glTF loader refuses an image
URI containing `..`. The open world draws them under its own lights, so they carry no spec or
emissive map.

**The winding trap (fixed at the source, 2026-10-11).** `glb()` used to mirror x AND reverse
every triangle, and the dungeons' loader (`loadPack`) undid both, so nothing showed until a file
went through the stock glTF loader. There the mirror alone is the whole right-to-left-handed
conversion, so the reversal turned every face inside out: the near wall was culled and the inside
of the far wall passed for the outside. The urn's planting showed through its wall, and the
obelisk and the sphere had the same fault, only less visibly. Now:

- `glb()` writes standard glTF: x mirrored, winding kept, counter-clockwise front faces with
  `f . n > 0`. Any loader draws it right.
- `loadPack` negates x back and leaves the winding alone.
- `client/test/glb_winding.test.mjs` reads every GLB under `public/models` and fails any whose
  faces disagree with their normals. It catches an inside-out export from any writer: these, the
  Heartwood lamps, the city modules, or a CC0 import.

The rule for any new writer is in CONTRIBUTING.md "Conventions worth keeping". A custom loader that
reads its own GLB undoes the mirror only.

The first urn was lidded and read as a soup tureen, and a modelled box ball read as a glossy
melon. `kingsgardens.ts` now plants the urn the way the parterres are planted: the gardens'
generated bush and the beds' flowers, sized to the urn's mouth (`URN_SOIL`).

The script is run by hand and is not part of `build_dungeon_props.mjs`. The dungeon builder
ignores these files: it merges only `<pack>.json`.
